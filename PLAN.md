# qcc — control center для агентов (Rust)

## Контекст

Нужен центр управления кодовыми агентами без собственного агентского цикла: под капотом работают
Claude Code, Codex и opencode. Главные требования: поддерживаемость, модульность и расширяемость
через плагины, которые могут писать и автор, и сторонние пользователи.

Решения, принятые в обсуждении:

| Вопрос | Решение |
| --- | --- |
| Интерфейс | Desktop на Tauri, фронтенд TypeScript + React |
| Топология | Отдельный демон `qccd`; приложение и CLI `qcc` — клиенты |
| Интеграция с агентами | Как в bb: провайдер = плагин-мост, структурные протоколы |
| Плагины | WASM-компоненты (wasmtime + WIT) |
| UI плагинов | Декларативная база + опциональный веб-бандл в iframe |
| Оркестрация | Только CLI + skill (без MCP) |
| MVP | Параллельные сессии, изоляция в git worktree, оркестрация |

Каталог `/home/quantick/projects/qcc` пуст, git не инициализирован. Машина на NixOS: нет rustup,
`pkg-config`, webkit, `wasm-tools`, `cargo-tauri`, pnpm и таргета `wasm32-wasip2`, поэтому первым
шагом идёт `flake.nix` с dev-окружением. Установлены claude 2.1.325, codex 0.166.0, opencode 1.19.4.

## Ключевые принципы (взяты из bb)

1. **Мост знает диалект, ядро знает ленту.** Плагин-провайдер переводит вывод агента в узкий набор
   семантических дельт (`turn.open`, `turn.boundary`, `item.open/close`, `item.text-delta`, `usage`,
   `interaction.request`, `session.ended`). Ядро собирает из них каноническую ленту `ThreadEvent`,
   выдаёт id, следит за порядком и жизненным циклом. Ядро нигде не ветвится по id провайдера.
2. **Нулевая привилегия встроенного.** Провайдеры, worktree и оркестрация — обычные плагины на
   публичном API. Если встроенному плагину чего-то не хватает, расширяется API, а не ядро.
3. **Каждый клиент рисует всё без кода плагина.** Декларативное описание UI обязательно,
   веб-бандл — необязательное улучшение.
4. **Права явные.** Плагин получает только то, что запросил в манифесте и что разрешил пользователь.

Зависимости направлены строго вниз: `domain` <- `runtime`/`store`/`protocol` <- `plugin-host` <-
`daemon`. `qcc-domain` не зависит ни от tokio, ни от wasmtime.

## Контракт плагинов

**Один мир WIT, событийная модель.** Плагин экспортирует `init()` (регистрирует вклады) и
`handle(event) -> result`, где `event` — типизированный variant. SDK превращает это в трейты
(`Provider`, `Environment`, `EventHook`, `Commands`, `Ui`) с реализациями по умолчанию, поэтому
автор реализует только нужное. Каждый экземпляр плагина — однопоточный актор с очередью. Это
снимает зависимость от async в компонентной модели: длинные операции (чтение stdout агента)
приходят в плагин как события, а не как блокирующие вызовы.

**Импорты хоста (права из манифеста):**

- `process` — запуск процесса и запись в stdin; stdout/stderr приходят событиями. Разрешённые
  исполняемые файлы перечислены в манифесте.
- `fs` — доступ в пределах выданных корней (каталог данных плагина, рабочий каталог треда).
- `http`, `kv` (хранилище плагина), `timers`, `log`.
- `threads` — создать, отправить, прочитать, дождаться тред. Основа для оркестрации.
- `deltas` — отдать дельты в ленту (только для провайдеров).

**Точки расширения:**

- `provider` — старт/возобновление сессии, ввод, прерывание, ответ на запрос разрешения,
  список моделей. Рукопожатие сообщает возможности (resume, fork, steer).
- `environment` — подготовка и удаление рабочего каталога треда.
- `event-hook` — подписка на события тредов.
- `commands` — команды для CLI (`qcc <plugin> <cmd>`) и палитры команд в приложении.
- `ui` — декларативные вклады (панель, вкладка треда, рендер элемента ленты, настройки) из
  фиксированного набора примитивов; опционально веб-бандл, который грузится в изолированный
  iframe и общается с плагином через `postMessage`-мост.

**Манифест `plugin.toml`:** id, версия, версия API, запрошенные права, путь к `.wasm`, опционально
путь к веб-бандлу. Плагины лежат в `~/.local/share/qcc/plugins/<id>/`, встроенные собираются вместе
с демоном и ставятся тем же путём.

## API демона и клиенты

- JSON-RPC по unix-сокету: `thread.spawn/send/stop/list/get`, `thread.events` (подписка с курсора),
  `interaction.resolve`, `plugin.list/install/enable`, `command.run`, `ui.contributions`.
- Tauri-бэкенд — тонкий прокси: держит `qcc-client`, отдаёт фронтенду `invoke` и канал событий.
  Бизнес-логики в нём нет.
- Типы TS генерируются из `qcc-protocol`, руками не дублируются.

## Оркестрация (CLI + skill)

- Демон передаёт каждой сессии `QCC_THREAD_ID` и `QCC_SOCKET`. Вызов `qcc thread spawn` изнутри
  агента автоматически записывает родителя.
- Команды: `qcc thread spawn|send|wait|show|list|stop`, у всех есть `--json`.
- Плагин `orchestration` поставляет skill с описанием этих команд. Провайдер подключает его к
  сессии штатным способом своего агента, без правок в домашних конфигах пользователя.
- `handoff` и `review` — команды плагина поверх `threads`, а не функции ядра.

## Этапы

Каждый этап заканчивается рабочим и проверяемым состоянием.

0. **Каркас.** `git init`, `flake.nix`, workspace, fmt/clippy/test.
1. **Домен и рантайм.** Типы, грамматика дельт, сборщик дельт, SQLite-журнал. Юнит-тесты сборщика
   на записанных последовательностях дельт.
2. **Хост плагинов.** WIT, wasmtime-хост с правами, SDK, `provider-echo`, testkit.
3. **Демон и CLI.** `qccd` + `qcc thread spawn --provider echo` со стримом событий: сквозной путь
   без реальных агентов.
4. **Реальные провайдеры.** Claude Code, затем ACP/opencode, затем Codex. Запросы разрешений.
   Форматы протоколов сверяются с установленными версиями CLI и записываются в фикстуры, а не
   берутся по памяти.
5. **Worktree.** `env-git-worktree`, статус и дифф.
6. **Desktop.** Список тредов, лента, композер, разрешения, вкладка диффа; декларативный UI
   плагинов, затем iframe-бандлы.
7. **Оркестрация.** Связи родитель/потомок, `thread wait`, skill, `handoff`/`review`.

В первой сессии реализации делаются этапы 0–3; дальше по одному этапу.

## Проверка

- `cargo fmt --check && cargo clippy --workspace -- -D warnings && cargo test --workspace`.
- Сборщик дельт: тесты на инварианты (id, порядок, закрытие без открытия, повторное закрытие).
- Testkit прогоняет каждый мост на записанном трафике агента и сравнивает ленту с эталоном.
- Сквозной тест этапа 3: поднять `qccd` во временном каталоге, `qcc thread spawn --provider echo
  --prompt hi --json`, проверить ленту и то, что после рестарта демона она читается из SQLite.
- Этап 4: ручной прогон с реальными `claude`, `opencode`, `codex` — сообщение, вызов инструмента,
  запрос разрешения, прерывание, возобновление.
- Этап 6: запуск приложения через `cargo tauri dev`, два параллельных треда в разных worktree.

## Риски

- **NixOS и Tauri**: webkitgtk и окружение сборки настраиваются во flake; если упрётся, этапы 0–5
  от этого не зависят.
- **Нестабильность протоколов агентов** (особенно `codex app-server`): изолирована внутри мостов,
  ловится testkit-ом на фикстурах.
- **Объём WIT-контракта**: начинаем с `provider` и `environment`, остальные точки расширения
  добавляются по мере появления встроенного плагина, которому они нужны.

## Справка для исполнителя

План исполняется в чистой сессии, поэтому всё нужное перечислено здесь.

- **Образец архитектуры** — репозиторий https://github.com/get-bb/bb (TypeScript). Его стоит
  склонировать во временный каталог и прочитать до начала этапов 1–2:
  - `docs/provider-bridge-protocol.md` — грамматика дельт и обязанности сборщика (основа для
    `qcc-domain` и `qcc-runtime`);
  - `docs/provider-plugin-api.md` — что объявляет провайдер, слои от моста до рендера;
  - `docs/system-overview.md` — модель данных (project, thread, environment, host);
  - `docs/worktrees.md` — управляемые worktree, `.worktreeinclude`, setup/teardown;
  - `plugins/provider-claude-code/src`, `plugins/provider-codex/src/bridge`,
    `plugins/provider-acp/src`, `examples/plugins/echo-provider` — рабочие мосты.
  Переносится схема, а не код: у нас мост живёт внутри WASM-компонента и получает процесс через
  импорт `process`, а не запускается отдельной программой.
- **Как bb запускает агентов**: Claude Code через Agent SDK (в Rust это `claude -p` с
  `--input-format stream-json --output-format stream-json`), Codex через `codex app-server`,
  opencode через `opencode acp`.
- **Окружение**: NixOS, cargo/rustc 1.99.0 без rustup (из таргетов есть только
  `wasm32-unknown-unknown` и `wasm32v1-none`), node 24, npm 11. Всё недостающее ставится через
  `flake.nix`, а не глобально.
- **Имена**: проект `qcc`, демон `qccd`, CLI `qcc`.
- **Порядок работы**: этапы 0–3 в первой сессии, затем по одному этапу; после каждого этапа
  проходят проверки из раздела «Проверка».
